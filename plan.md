# Live battle play plan

## Scope and existing behavior

Target `/battle/play/[id]` (the `/battle/play/` route family). Keep the existing Convex-backed 3–5 NFT roster, three-card lineup, active/reserve cards, per-card HP, and legacy one-card matches working. Update the NFT move-generation and battle data paths only where needed to support the new rules.

Today `convex/schema.ts` stores fire (0), water (1), and grass (2) NFT types and a speed stat. `convex/battle.ts` uses speed only to pick the *first* turn; later attacks alternate, and its existing 1.5×/0.65× type matchup uses the attacker's NFT type because moves have no type field. `convex/nft.ts` generates four free-form moves without an enforced element or utility action. On the live page, the NFT images sit inside square, bordered buttons even when the artwork's dimensions differ; the inspect panel is an anchored sidebar. Both the local battle top bar and the global `Navbar` can appear.

**Production security follow-up:** battle mutations still trust a caller-supplied wallet address. Before treating competitive results or credit rewards as secure, authenticate actions with a server-verified wallet challenge/signature and verify roster ownership against trusted chain data. Browser wallet connection or synced NFT ownership alone does not prove who called a Convex mutation.

## Ordered implementation tasks

1. **Fix live-card presentation, enlarge cards on the table, and remove the top navigation.** In `components/battle/BattleNFTCard.tsx` and `components/battle/tcg/battle.css`, size the clickable card and any outline to the *rendered artwork's actual aspect ratio*, including unusual portrait/landscape images. Avoid a square button, padded frame, `object-fit: contain` letterboxing inside a mismatched border, or a larger border box with empty space around the image. Increase the size of cards placed on the battle table—especially the two active cards—so their art is clearly visible; adjust board positioning and responsive sizes so larger cards do not overlap each other, the lineup, the rails, or action controls. Use an image-fitting outline/overlay and consistent behavior for active, reserve, opponent, hover, focus, and missing-image fallbacks; test responsive layouts and intrinsic-size loading. Remove `battle-topbar` from `app/battle/play/[id]/page.tsx` and suppress the site-wide `Navbar` on this route without removing it from other pages. Keep essential log/effects controls and any necessary way back to the arena in a compact, non-nav battle control area; reclaim the vertical space.

2. **Turn CARD INSPECT into a temporary, polished pop-up.** Open it only after explicitly selecting a card, not as a permanent sidebar. Make the artwork the visual centerpiece with no padded or differently sized box/border around it; arrange name, elemental type, HP, speed, other real stats, moves, and applicable switch control in a deliberate battle-themed overlay. Dismiss with close button, Escape, or backdrop; restore focus to the triggering card, prevent accidental turn submission, and keep it usable by keyboard/touch and on narrow screens. Decide whether the backdrop blocks interaction while open and implement matching dialog semantics/focus behavior. Preserve separate move selection and inspection actions; switching a card must remain explicit.

3. **Define typed move data and generate exactly four valid moves per NFT.** Extend `nftMoveSchema` and shared UI types with a stable move kind (`attack`, `protect`, `switchout`) and an elemental type for each attack. Generate **three attacks of the NFT's own element** plus **exactly one** utility move, either Protect or Switchout. The card's name/description can flavor attack names, but generated text cannot change the actual gameplay type or kind. Validate AI responses server-side; update `getFallbackMoves` and saved-move handling in `convex/nft.ts` so both generated and fallback sets meet this invariant. Handle older saved moves and locked battle snapshots explicitly (version or normalize on read/lock) without silently breaking ongoing/legacy matches or treating an arbitrary old move name as Protect. Render all four moves with visible type/utility and real, server-backed effects on the battle page and in inspection.

4. **Apply elemental matchups to the selected attack move.** In `convex/battle.ts`, calculate effectiveness from the chosen attack's *move type* versus the defending NFT's type, not from the attacker by default. Keep and document the existing cycle: water > fire, fire > grass, grass > water; advantage 1.5×, disadvantage 0.65×, same type 1× (or deliberately rebalance and test both directions). Protect/Switchout deal no damage and cannot be submitted as an attack. Validate move identity, kind, elemental type, active card, and eligible target server-side; return/store actual damage and effectiveness for the battle log and UI. Avoid client-supplied damage or type multipliers.

5. **Make speed govern attack priority, not just the opening move.** Replace the strictly alternating attack resolution for new matches with an authoritative round/action flow: collect one valid action from each player, then resolve actions in priority order. Protect always resolves before attacks; define Switchout priority explicitly (proposed: after Protect, before attacks); order attacks by the *currently active cards'* speed, with a documented deterministic tie rule. Re-evaluate speed after switches/KO replacements. Specify what happens when the first action KOs the other card, when a player needs a forced replacement, on timeout/disconnect, and on duplicate/stale submissions; ensure only one result/reward can be committed. Persist pending choices and resolved action events in Convex so refreshes and both clients see the same state. Keep a compatibility path for existing alternating-turn battle records.

6. **Implement Protect and Switchout as the fourth move.** Protect takes priority, blocks all opponent attack damage against the card for that round on success, and has success probabilities 100%, 50%, 25%, etc. for consecutive uses by that card; reset its streak when that card takes a different action or is switched out. Decide and document failure behavior and use a server-side recorded roll so clients agree and retries cannot reroll. Switchout prompts selection of a living reserve from the player's **three-card battle lineup** (not an unselected lobby-roster NFT), validates the chosen card server-side, and resolves under the round-priority rules. Preserve the existing forced replacement after KO as a separate, no-extra-turn flow; prevent switching to the same, knocked-out, or unselected card. Show success/failure, blocked damage, card changes, and turn/round state in the log and visual feedback without inventing damage values.

7. **Verify rules, compatibility, and presentation.** Add focused tests in `tests/battle.test.mjs` (and move-generation tests as needed) for each element pairing, attack type validation, three attacks plus one utility, speed order and ties, Protect-before-attack and its halving/reset sequence, failed Protect, Switchout eligibility/order, simultaneous choices, KO/replacement, invalid/duplicate/stale submissions, reload/disconnect, and old battle records. Exercise two-wallet live play plus mobile/desktop card proportions, visibly larger table cards without overlap, unusual image aspect ratios, missing art, popup focus/close behavior, route-only navbar removal, and reduced motion. Run the project test suite, TypeScript check, lint/format check, and production build; fix regressions introduced by this work.

8. **Make multiple focused commits with Conventional Commit messages so changes are easy to track and push to the remote.** For example: `fix(battle): align card outlines with NFT artwork`, `feat(battle): add typed attacks and elemental matchups`, `feat(battle): resolve speed-priority rounds and utility moves`, `test(battle): cover priority and protect rules`. Review the diff/status before each commit and exclude unrelated or secret files. Push only after confirming the intended branch/remote and obtaining authorization; do not treat this planning task as authorization to commit or push now.

## Implementation status

- Tasks 1–6 are implemented for newly created matches; legacy matches keep alternating-turn rules. Player one wins equal-speed attack ties. Protect resolves before Switchout, then attacks. A KO cancels the defeated card's unresolved action. If only one player locks an action, a 90-second server timer ends the stalled match in that player's favor without issuing credits.
- Task 7: automated battle tests, TypeScript, formatting checks, and the production build pass. A two-wallet browser playthrough and visual checks at desktop/mobile sizes remain outstanding; the available browser automation could not launch Chromium on this OS.
- Task 8: focused Conventional Commit messages have been used locally. No push has been performed.
